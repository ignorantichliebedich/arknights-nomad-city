# 四人联机延迟排查

## 同步与恢复

每次有效操作先完成规则裁定与 SQLite 持久化，再返回回执并同步各玩家视图。WebSocket 协商 `permessage-deflate`，压缩级别 3、并发上限 2；双方消息均不沿用上一条消息的压缩字典。未协商压缩的连接继续使用 JSON。完整日志和私牌可见性按原规则保留，数据库仍使用 WAL 与 `synchronous=FULL`。

浏览器只在新连接收到第一份状态时补交待核对指令。朋友的行动和上下线引起的状态更新不会再次提交自己的指令。建立连接、首次同步或等待操作回执超过 15 秒时，浏览器显示重新同步提示并按退避间隔重连；补交沿用原指令编号，服务器依据持久化回执避免重复执行。刷新也走同一恢复流程。15 秒是网络恢复阈值，游戏行动仍没有倒计时。

参数依据 [ws 压缩说明](https://github.com/websockets/ws#websocket-compression)；压缩增加 CPU 与内存成本，因此采用低压缩级别和有界并发。入站 16 KiB 限制对解压后的消息同样生效。

## 后续定位

服务端只在超过阈值时输出结构化记录，字段包含房间、状态版本与耗时，不包含私牌、指令正文或凭证：

- `slow-room-command`：接收到处理结束合计至少 250 ms。`queueMs` 为等待房间串行队列的时间；`processMs` 为出队后的处理时间；`saveMs` 为 SQLite 保存时间，包含于处理时间内。`outcome` 区分执行、回执重放和拒绝。
- `slow-room-broadcast`：生成与提交各席同步、调度人机合计至少 100 ms。
- `slow-state-write`：单席消息提交至本机 WebSocket 发送完成回调至少 500 ms，包含压缩及本机发送队列。`jsonBytes` 是压缩前大小，`compressed` 表示连接是否协商压缩。此回调不表示朋友已经收到消息。

获得对应版本上线确认后，卡顿时记录房间码、大致时间及操作；对照上述记录、容器 CPU/内存与服务器出口带宽。处理很快但浏览器迟收状态时，继续查公网链路及音乐/图片下载是否挤占出口。处理或保存慢时，再按对应分段检查规则计算、磁盘及同时运行的任务。

本地自动验证包括：四席协商压缩后的真实接收字节、完整日志与私牌投影、无压缩兼容连接、四浏览器延迟回执期间的提交次数、回执丢失后的超时重连和刷新恢复，以及原有并行盖放与采集屏障。测试只使用隔离数据库。
