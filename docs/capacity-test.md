# 2026-10-18 承压测试

## 容量结论

连接上限保持 128 个，相当于 32 桌四人局；同一公网 IP 上限仍为 16 个。按本轮后期对局、每桌约两秒一次操作的负载，服务器机内常规处理通过 128 个连接，操作回执和四席状态均完整送达，第 129 个连接返回 503。

实际容量首先受到本机到服务器链路的有效吞吐限制：未压缩和压缩两组均在约 2.9Mbps 附近出现排队。未压缩四桌常规负载的同步 P95 为 3.48 秒；同一隔离实例开启 v0.5.3 所用的压缩参数后，四桌为 0.15 秒，十六桌为 0.10 秒，三十二桌再次出现约 3.64 秒排队。大量同时操作还会叠加主线程排队：压缩后机内十六桌同时盖牌的 P95 为 2.63 秒，事件循环最大延迟 1.59 秒。平均 CPU 低不能替代峰值延迟检查。

规划容量要看高峰。所有测试桌同时进入盖牌、每桌四人同时提交时，压缩后四桌的同步 P95 为 1.52 秒、八桌为 3.27 秒。因此在相同链路下，压缩方案上线后的保守常态容量按 **4 桌、16 人**规划；较少同步操作时可容纳更多玩家。音乐和图片首次下载同样使用出口，应留出余量。该建议不改变连接和房间配置。

## 公网链路实测

“同步延迟”从一位模拟玩家发出指令开始，到该桌四位玩家都收到对应状态版本为止。P95 表示 95% 的样本不超过该耗时。以下均为四人企业扩展、种子 52 的第六回合真实状态及合法操作，包含约 740 条既有日志。

| 场景 | 人数 / 桌数 | 未压缩同步 P95 | 压缩后同步 P95 |
| --- | --- | ---: | ---: |
| 各桌错峰常规操作 | 16 人 / 4 桌 | 3,483 ms | 150 ms |
| 各桌错峰常规操作 | 32 人 / 8 桌 | — | 127 ms |
| 各桌错峰常规操作 | 64 人 / 16 桌 | — | 100 ms |
| 各桌错峰常规操作 | 128 人 / 32 桌 | — | 3,644 ms |
| 同时盖牌及后续同步操作 | 4 人 / 1 桌 | 3,454 ms | 250 ms |
| 同时盖牌及后续同步操作 | 16 人 / 4 桌 | — | 1,521 ms |
| 同时盖牌及后续同步操作 | 32 人 / 8 桌 | — | 3,269 ms |

未压缩错峰负载 1、2、4 桌的有效吞吐分别约 1.36、2.62、2.89Mbps；四桌时服务端平均 CPU 约占单核 3%，却有 20 次调度因等待同步而错过。压缩后十六桌约 2.72Mbps、CPU 25%；三十二桌吞吐约 2.87Mbps、CPU 28%，错过 193 次调度。等待出现在传输排队阶段，不能用增加在线连接限额解决。

## 方法与范围

机内常规处理（未压缩）：

| 人数 / 桌数 | 全桌同步 P95 | 平均 CPU（单核百分比） | 进程采样峰值 RSS | 成功 / 错误 |
| --- | ---: | ---: | ---: | ---: |
| 4 人 / 1 桌 | 38 ms | 2% | 121 MiB | 15 / 0 |
| 16 人 / 4 桌 | 36 ms | 5% | 122 MiB | 60 / 0 |
| 32 人 / 8 桌 | 40 ms | 11% | 126 MiB | 120 / 0 |
| 64 人 / 16 桌 | 39 ms | 21% | 126 MiB | 240 / 0 |
| 128 人 / 32 桌 | 42 ms | 41% | 130 MiB | 480 / 0 |

机内压缩后的同步盖牌高峰，4 / 8 / 16 桌的全桌同步 P95 分别为 607 / 1,203 / 2,635 ms；十六桌时已超过两秒阈值，因此按规则停止升档。该峰值测试提示，出口扩容后还应优化同步广播和主线程工作，不能直接把常规场景的 128 连接结果作为高峰承载承诺。

- 云端使用与正式实例相同的 v0.5.2 镜像（Node.js 24.21.0），临时容器限制 1.25 核、512MiB。数据库由工具生成在容器自己的临时目录，沿用 WAL 与 `synchronous=FULL`；测试端另置容器，限制 0.5 核。正式数据卷、容器与反向代理配置独立保留。
- 压缩对照只在临时实例中改变 WebSocket 协商参数：level 3 / memLevel 7、并发 2、双方无跨消息字典。规则与存档版本相同。此项验证压缩参数的效果，公网正式服务仍为 v0.5.2。
- 服务端处理测试在云主机回环网络运行；公网测试从本机通过独立 SSH 隧道连接临时实例，测试端接收真实 WebSocket 数据。该方式经过公网出口，并保留多个逻辑连接；共享 SSH TCP 连接会影响排队和丢包表现。数字代表本次线路的模拟结果，朋友各自线路仍需结合实际对局观察。
- 负载分档为 1、2、4、8、16、32 桌，按场景选用。每档调度窗口 20–30 秒，报告另记录实际完成耗时。常规场景在两秒内均匀分散各桌操作；高峰场景各桌同时发起，并在角色阶段让四席并行提交。每条指令使用独立编号和合法选择令牌，等待全桌对应状态后再继续。响应跟不上时记录错过的调度，不把发不出去的操作计为成功。
- 记录回执与全桌同步的 P50/P95/最大值、成功数、错误、调度缺口、真实接收字节、服务端 CPU/RSS、事件循环延迟、CPU 限流与 SQLite 回执及完整性。媒体加载和浏览器绘制另占资源，本次不计入模拟客户端。
- 公网测试期间每 2.5 秒检查正式健康接口，连续两次失败或超过 1.2 秒即关闭测试连接；单档同步 P95 超过两秒后停止升档。健康保护均未触发，常规负载组健康 P95 低于 80ms，同步高峰组最高为 310ms。所有已记录指令无裁定失败，回执数与完成同步数一致。

原始汇总保存在本机私有 `.data/load-tests/`；对局全量数据和凭证不进入公开仓库。

## 本地复测

```powershell
pnpm load:test --tables 1,4,8,16,32 --seconds 30 --interval-ms 2000
pnpm load:test --tables 1,4,8 --seconds 30 --phase select --schedule burst
pnpm load:test --tables 1,4 --seconds 30 --compression off
```

默认启动两个独立 Node.js 进程并自动选择空闲端口；服务端创建新的合成数据库，不接受原存档路径。默认结果写入忽略目录 `.data/load-tests/`。`--output` 可指定报告文件；`--output -` 输出纯汇总。`--compression native/on/off` 用于对照，`--schedule staggered/burst` 控制各桌是否同时提交，`--phase actions/select` 选择后期主要行动或并行盖牌。

`server` / `client` 模式供隔离环境使用；客户端仅允许回环地址，并校验游戏端与控制端的同一实例标识。工具不会对普通游戏实例发起压测。Docker 测试端口仅映射服务器回环地址，正式对外入口不增加测试接口。云端承压测试需由用户明确提出，结束后销毁临时容器与隧道；此授权不等于正式版本部署授权。
