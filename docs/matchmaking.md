# 公开招募与匹配

首页创房许可下方的“匹配同行者”和“找房间”进入同一招募大厅。玩法区分本体、企业扩展、感染者常规与感染者企业家抉择；人数默认不限，也可选择 2、3、4 人。

匹配先检查相容队列。达到人数后自动创建一桌，所有人仍需确认准备，再由房主开局。人数不限的玩家可补足任一对应队列；全为不限人数时，至少两位即可组桌。队列按登记顺序分配，自动组桌中的同名昵称增加区分后缀。

登记后保留一秒会合窗口，让同时发起的请求优先组桌；队列不足则寻找在线公开房间。同玩法、相同约定人数或人数不限的房间可接纳匹配。指定人数的玩家加入不限人数房间时，会确定该桌人数，并重置准备。明确约定三人局就需三席入座，不能提前以两人开始；人机同样占用目标人数内的席位。

## 招募与席位

- 新房默认私人邀请、人数不限；原有房间保持私人。房主可在创房时或房间内开启公开招募，并设定本桌人数。
- 大厅按玩法及人数筛选，展示房间码、房主昵称、玩法及入座／准备人数；不展示凭证、私牌、牌库、对局内容或排队者身份。仅展示房主在线、仍有空席的待开局房间，分页每页 20 桌。
- 选择公开房间后仍在服务端校验玩法、容量及招募状态。旧目录、争抢最后一席和房主关闭招募均不会绕过检查；已有有效凭证优先恢复原席位。
- “离开席位”在开局前释放本席，房主离座时把房主交给其余玩家。返回上一级保留席位；开局后席位继续锁定。

## 一致性与恢复

匹配登记、整组建房和席位分配在同一 SQLite 事务中完成；失败一起回滚，成功提交后再同步房间。队列使用服务端状态并持久化，重复登记和轮询返回同一分配结果。席位恢复复用同一高熵凭证，数据库只保存摘要。凭证经请求头发送，不进入目录或 URL。

浏览器每 2.5 秒查询本次匹配，每 5 秒刷新房间目录。取消与匹配分配竞争时，尚未入座的分配被释放；取消记录也会阻止迟到的登记请求重新入队。页面刷新接续同一请求，服务重启可恢复等待与分配。停止心跳 90 秒的等待请求过期，分配后 60 秒未连接的席位释放；已验证入座及已开局的席位保留。旧结果保留一天供恢复，取消记录保留十分钟。

目录使用独立的待开局摘要索引，查询不读取已保存对局正文。匹配队列有全局及每网络名额限制，接口沿用来源校验、请求体大小、频率限制与房间容量限制。

默认最多 1000 个匹配请求、同一网络 4 个待匹配／待入座请求，分别由 `MAX_MATCHING` 和 `MAX_MATCHING_PER_IP` 配置；已验证入座的请求不再占用排队名额。Docker 与 Windows 运行包均包含共用的大厅类型与配置模块。

`tests/matchmaking.test.ts` 覆盖人数及玩法组合、优先组桌、补入、取消竞争、过期、恢复及事务回滚；`tests/lobby-server.test.ts` 验证真实 HTTP/WebSocket、凭证、公开投影、权限、容量及开局人数。浏览器检查见 `tests/browser/recruitment.spec.ts`，并在手机及桌面视口核对键盘操作与窗口边界。
