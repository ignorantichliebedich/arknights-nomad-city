# 并行盖放与采集

每回合的角色盖放，以及回合末的采集路线、路费收款人选择，允许所有席位同时操作。每位玩家明确确认后进入等待；全部玩家完成才推进。两人局移出供应设施、企业升级、行动中的角色能力与事件继续按各自规则顺序执行。

## 结算约定

角色确认后从本人的手牌移入盖放区，其他玩家只能看到完成状态和手牌数量。盖放牌的身份仍按原有揭示规则公开。

采集确认之前可以增减资源点，系统按现有路费算法合并共用航道。确认路线后选择每条收费航道的收款人；完成全部选择后锁定方案。空方案也需要点击确认。路费支出、路费收入与资源产出均等到全员完成后执行，日志按本回合大总统开始的玩家顺序记录，不依赖网络请求到达顺序。

路费预算使用本阶段开始时持有的金券；本阶段应收路费不能提前支出。这是为并行玩法明确的联机流程约定。它使已展示的路线和费用保持有效，也避免玩家通过先后点击影响别人的预算。角色、企业或样式能力触发的额外单人采集保留原有时机。

## 状态、并发与恢复

- 服务端 `GameState.parallel` 保存阶段编号、起始玩家顺序，以及每席位独立的待选项、计划队列、待结算效果、完成状态和选择版本。全局 `decision` 保留第一个未完成的代表决策，兼容存档工具与串行模拟。
- 玩家视图只返回本人的决策，以及各席位完成与否。其他人的路线、收款人选择、队列和待结算效果不外传；计划操作日志仅本人可见，确认状态公开。
- 客户端指令携带房间版本和本人的选择令牌。仅在同一并行阶段、本人待选项未变化时允许旧房间版本；错席位、本人旧选择、未来房间版本或跨阶段令牌仍被拒绝。相同指令编号首先查持久化回执，重复请求不重复执行。
- 成功操作仍按房间串行、事务保存、再广播。阶段内只修改提交者的计划；最后一条确认在同一次保存中完成统一结算和阶段推进。
- 断线不会代替玩家确认。每条计划修改都保存，可在选路或选择收款人中刷新、断线、重启服务后继续。
- 前端用本人选择版本管理本地预览。朋友操作或上下线只更新完成状态，不清空抬牌、费用核对或收款人预览。

## 既有房间

既有 `founders-2023.1` 存档保留。遇到旧的角色盖放或回合末采集待选项，视图以副本生成并行状态，下一条有效指令才持久化；已经盖放的牌、已经取得的资源与已经付出的费用保持原值。

若旧存档正在支付某人的路费，先完成该人的既有支付链；进入后续玩家的采集规划时切换为并行。能力触发的单人采集不会被当作回合末屏障。升级前须备份数据库并保存发布记录。

## 验证范围

规则与服务场景覆盖 2、3、4 人任意顺序盖放、空采集明确确认、共用航道与撤回、多个收款人、预算固定、交错选择、确定性结算、私密信息隔离、旧存档投影、同时提交、重复请求、旧选择令牌和服务重启。

浏览器场景用四个独立席位检查抬牌与收款人预览保留、状态进度、离线最后一席恢复、路线刷新恢复，以及最后确认后的资源数值变化。具体通过记录见 [验收记录](acceptance.md)。
