# 四人联机延迟排查

2026-10-18 的多房间、同步盖牌与公网容量实测见 [承压测试报告](capacity-test.md)。

## 同步与恢复

每次有效操作先完成规则裁定与 SQLite 持久化，再返回回执并同步各玩家视图。v0.9.4 的浏览器声明 `stateSync: 1`：首次连接收到完整状态，之后只接收变化字段、数组变化和新增日志。服务端先为各席生成可见视图，再按该连接的上一份视图计算差异；私牌、隐藏选择与私人日志沿用原投影边界。完整历史保留在客户端，数据库仍使用 WAL 与 `synchronous=FULL`，存档格式及规则版本保持兼容。

增量消息使用独立于房间版本的连接序号，因此同一房间版本下的上下线变化也可同步。完全相同的状态跳过发送，变化过大时回退完整快照。旧客户端未声明协议版本时继续接收完整 JSON，新浏览器也可连接旧服务。WebSocket 同时协商 `permessage-deflate`，压缩级别 3、并发上限 2，双方均不沿用上一条消息的压缩字典；没有协商压缩的连接同样可以使用增量同步。

浏览器只在新连接收到第一份状态时补交待核对指令。朋友的行动和上下线引起的状态更新不会再次提交自己的指令。回执先到时，继续等待对应房间版本的状态再恢复操作，避免在旧画面上提交下一条指令。发现增量基线不一致时自动重新连接，并从完整快照恢复。建立连接、首次同步或等待操作结果超过 15 秒时同样按退避间隔重连；补交沿用原指令编号，服务器依据持久化回执避免重复执行。刷新也走同一恢复流程。15 秒是网络恢复阈值，游戏行动仍没有倒计时。

参数依据 [ws 压缩说明](https://github.com/websockets/ws#websocket-compression)；压缩增加 CPU 与内存成本，因此采用低压缩级别和有界并发。入站 16 KiB 限制对解压后的消息同样生效。

## 2026-11-17 本地合成对局测量

运行 `pnpm network:measure`，在独立的二人本体、四人企业及四人感染者专家模式中推进至第六回合，补齐为 1,300 条合成历史记录，再执行 60 次合法行动。每一步均将收到的增量还原结果与各席完整投影逐项核对。工具不读取已有房间，也不访问云服务器。

以下是各席合计的压缩状态帧估算字节数，不含首次快照、回执、心跳、握手、TCP/TLS、图片或音频。原广播与增量使用相同的压缩参数；真实 WebSocket 字节另由服务回归测试覆盖。

| 场景           | 操作数 |  原完整广播 |  增量广播 | 状态流量减少 |
| -------------- | -----: | ----------: | --------: | -----------: |
| 二人本体       |     60 | 1,694,175 B |  82,813 B |        95.1% |
| 四人企业       |     60 | 3,632,105 B | 140,071 B |        96.1% |
| 四人感染者专家 |     60 | 3,824,181 B | 141,210 B |        96.3% |

四人企业的单次广播 P95 从约 63.6 KB 变为 3.3 KB；这两种广播在出口独占 3 Mbps 时，纯传输时间分别约 170 ms 和 9 ms。它们是本地合成状态的传输量估算，不是公网响应时间或容量承诺。图片与音乐仍共享出口，首次连接也仍需要完整快照。

复现增量或旧版完整状态的隔离承压：

```sh
pnpm load:test --tables 1,4 --seconds 10 --state-sync delta --output .data/load-tests/delta.json
pnpm load:test --tables 1,4 --seconds 10 --state-sync legacy --output .data/load-tests/legacy.json
```

只在本机或明确隔离的测试实例执行，不对正在游玩的云端房间发送压测操作。

## 2026-10-18 只读测量

在服务器内读取四人存档，仅输出汇总大小和纯函数耗时，不导出玩家状态，也不执行持久化行动。下表为四个玩家视图的合计 JSON 大小，压缩列使用本轮相同的 level 3 / memLevel 7；实际 WebSocket 还包含少量协议字节。

| 场景          | 日志条数 | 原始字节 | 压缩字节 |  减少 |
| ------------- | -------: | -------: | -------: | ----: |
| 第 5 回合行动 |      634 |  275,194 |   37,931 | 86.2% |
| 第 8 回合终局 |    1,288 |  499,873 |   62,852 | 87.4% |
| 第 8 回合终局 |    1,278 |  492,174 |   59,636 | 87.9% |
| 第 8 回合终局 |    1,336 |  503,833 |   61,337 | 87.8% |

两轮采样中，四席投影合计约 9–47 ms；可执行的第 5 回合行动纯函数约 7–10 ms。服务器空闲采样负载低、可用内存超过 1 GiB。这些数值支持先处理同步流量和重复提交，不能替代卡顿发生时的峰值记录，也不能直接换算公网体验改善倍数。

## 后续定位

服务端只在超过阈值时输出结构化记录，字段包含房间、状态版本与耗时，不包含私牌、指令正文或凭证：

- `slow-room-command`：接收到处理结束合计至少 250 ms。`queueMs` 为等待房间串行队列的时间；`processMs` 为出队后的处理时间；`saveMs` 为 SQLite 保存时间，包含于处理时间内。`outcome` 区分执行、回执重放和拒绝。
- `slow-room-broadcast`：生成与提交各席同步、调度人机合计至少 100 ms。
- `slow-state-write`：单席消息提交至本机 WebSocket 发送完成回调至少 500 ms，包含压缩及本机发送队列。`jsonBytes` 是实际完整或增量消息压缩前的大小，`stateType` 区分两种消息，`compressed` 表示连接是否协商压缩。此回调不表示朋友已经收到消息。

获得对应版本上线确认后，卡顿时记录房间码、大致时间及操作；对照上述记录、容器 CPU/内存与服务器出口带宽。处理很快但浏览器迟收状态时，继续查公网链路及音乐/图片下载是否挤占出口。处理或保存慢时，再按对应分段检查规则计算、磁盘及同时运行的任务。

本地自动验证包括：四席协商压缩后的真实接收字节、完整日志与私牌投影、无压缩兼容连接、四浏览器延迟回执期间的提交次数、回执丢失后的超时重连和刷新恢复，以及原有并行盖放与采集屏障。测试只使用隔离数据库。
